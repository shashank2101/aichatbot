## The pipeline is now a LangGraph (`app/agents/graph.py`)

`orchestrator.handle_question()` used to be a hand-written function with an
if/elif ladder and a `while True` retry loop. That logic is now a
`StateGraph` — every pipeline stage from your original docstring is a node,
and the retry loop is a real graph cycle (`satisfaction → retry → execute`)
instead of a Python `while`. `orchestrator.py` is now just a thin adapter:
build initial state → `GRAPH.invoke()` → translate the final state into the
HTTP response shape + write the observability log.

**Nodes that call the LLM ("agent" nodes)** — these are the ones actually
worth calling agents, since they carry a system prompt to a model (or its
offline stub):
- `text2sql` — NL question → SQL
- `answer` — rows → natural-language answer
- `satisfaction` — judges the answer, decides whether to loop
- `retry` — re-runs `text2sql` with a nudged prompt

**Deterministic nodes** (regex, SQL, dict filtering — no model call):
`intent`, `jailbreak`, `off_topic`, `greeting`, `cache`, `no_sql`,
`table_gate`, `execute`, `mask`, `finalize`.

Graph shape:

```
intent ─┬─ jailbreak_attempt ──────────────────────────────→ END
         ├─ off_topic ───────────────────────────────────────→ END
         ├─ greeting ────────────────────────────────────────→ END
         └─ (else) → cache → text2sql ─┬─ no sql ────────────→ END
                                         └─ table_gate ─┬─ denied → END
                                                          └─ execute ─┬─ error → END
                                                                       └─ mask → answer → satisfaction ─┬─ done → finalize → END
                                                                                                          └─ retry → execute (loop)
```

`audit_report_agent.py` stays a standalone single-shot agent (triggered by
`GET /audit-report/{id}`, not part of the chat graph) — it doesn't have a
retry/branch structure to justify graphing it, it's one LLM call.

## Request pipeline (`POST /chat`)

`main.py:chat()` → `orchestrator.handle_question()` → `GRAPH.invoke()`, which runs:

1. **Intent + jailbreak check** (`intent_agent`) — pure regex/keyword, no
   DB or LLM touched yet. Off-topic → polite deflection. Jailbreak attempt →
   refuse + flag (logged, never reaches SQL generation).
2. **Cache lookup** (`cache.find_similar`) — fuzzy-matches against past
   questions scoped to the same `role:region`, reusing prior SQL if similar
   enough (`config.CACHE_SIMILARITY_THRESHOLD`).
3. **Text-to-SQL** (`text2sql_agent.generate_sql`) — rule-based templates by
   default (`config.USE_LLM=False`), or a real Azure OpenAI call otherwise.
   Every candidate SQL string is checked by `is_safe_select()` before use.
4. **RBAC table gate** (`mask_agent.check_table_access`) — blocks execution
   outright if the SQL references a table the role can't see at all.
5. **Execute** (`executor_agent.execute`) — resolves which physical
   store(s) to hit via `stores_for_user()`, runs the SQL, then applies
   **row-level** RBAC filtering on top of table-level (see DB_SCHEMA.md
   "Row-level RBAC" section) since `primary` physically holds all regions.
6. **Column mask** (`mask_agent.mask_rows`) — strips sensitive columns
   (e.g. `unit_cost`) per role before rows are ever handed to the LLM.
7. **Answer generation** (`answer_agent.generate_answer`) — natural-language
   summary from the masked rows only.
8. **Satisfaction check** (`satisfaction_agent.is_satisfied`) — if
   insufficient, loop back to step 3 with a nudged prompt, up to
   `config.MAX_SATISFACTION_RETRIES` times.
9. **Log + cache store** — one row into `obs_logs`; SQL cached for reuse if
   this wasn't already a cache hit.

## LLM usage & offline mode

`app/llm.py` is the single choke point for all model calls. If
`AZURE_OPENAI_API_KEY` + `AZURE_OPENAI_ENDPOINT` are both set (they now are,
via `.env`), every agent call goes to your Azure deployment. If either is
blank, every call **automatically** returns a deterministic offline stub
(`llm._offline_stub`) keyed by `mode` (`answer`/`satisfaction`/`audit_report`),
so the app still runs end-to-end with zero API cost/keys — useful for
frontend dev without burning tokens.

## Where the frontend should point

All routes are defined in `app/main.py`, CORS is already wide open
(`allow_origins=["*"]`). Once the FastAPI app is running (see README.md),
your frontend talks to:

| Route | Method | Auth | Purpose |
|---|---|---|---|
| `/login` | POST | — | returns `{token, username, role, region, full_name}` |
| `/chat` | POST | token in body | main Q&A pipeline |
| `/chat/feedback` | POST | Bearer | thumbs up/down on a `log_id` |
| `/dashboard/metrics` | GET | Bearer | inventory/audit/discrepancy/AI aggregate stats |
| `/alerts` | GET | Bearer | deterministic alert feed (no LLM) |
| `/audit-report/{warehouse_id}` | GET | Bearer | LLM-generated audit summary for one warehouse (now also returns `high_severity_count` + `risk_stats`) |
| `/audit-report/consolidated` | GET | Bearer | LLM-generated AI insights summary across every warehouse in the caller's RBAC scope |
| `/ingest/upload-csv` | POST | Bearer, admin/manager | CSV file upload version of the ERP push — parses the file, then runs it through the exact same `preprocessing.process_ingest_push()` validation/sync pipeline as `/ingest/push` |
| `/warehouses` | GET | Bearer | RBAC-scoped warehouse list |
| `/admin/observability` | GET | Bearer, admin only | analytics dashboard |
| `/ingest/push` | POST | Bearer, admin/manager | simulated ERP push button |
| `/me` | GET | Bearer | current user info |
| `/health` | GET | — | liveness check |

`Bearer` routes expect `Authorization: Bearer <token>`; `/chat` instead
expects the token inside the JSON body (`ChatRequest.token`) — that
inconsistency is in the existing code, not something I changed; flagging it
in case you want it unified for the frontend.

If `frontend/dist/` exists at the project root, `main.py` also serves it
directly as a SPA (catch-all route + `index.html` fallback) — so in
production you can run just the FastAPI process and it'll serve both API and
UI on one port.

## Role → Page Access

Every logged-in role sees Chat, Dashboard, Alerts, and Audit Reports (each still
row/column-scoped server-side per `rbac.py`). Two pages are further gated by role,
enforced both in the sidebar (`AppShell.tsx`'s `NAV` list) and as a route guard
(`App.tsx`'s `RoleRoute`) — so hiding the link and navigating to the URL directly
are both covered:

| Page | Route | admin | manager | auditor | viewer |
|---|---|---|---|---|---|
| Chat | `/app/chat` | ✔ | ✔ | ✔ | ✔ |
| Dashboard | `/app/dashboard` | ✔ | ✔ | ✔ | ✔ |
| Alerts | `/app/alerts` | ✔ | ✔ | ✔ | ✔ |
| Audit Reports | `/app/audit-reports` | ✔ | ✔ | ✔ | ✔ |
| Data Upload | `/app/data-upload` | ✔ | ✔ | — | — |
| Observability | `/app/observability` | ✔ | — | — | — |

The underlying API routes enforce the same rule independently (`/ingest/*` checks
`role in ("admin","manager")`, `/admin/observability` checks `role == "admin"`) —
the frontend gating is a UX nicety, not the actual security boundary.

## Frontend

React + TypeScript + Vite + Tailwind v4 + React Router. Your uploaded pages
and components are wired up as-is under `frontend/src/pages` and
`frontend/src/components`. What I added (wasn't in your upload):

- **`src/context/AuthContext.tsx`** — every page imports `useAuth()` from
  here but it didn't exist. Holds `{ user, login, logout }`, persists the
  logged-in user to `localStorage` so a page refresh doesn't log you out.
- **`package.json`, `vite.config.ts`, `tsconfig*.json`, `index.html`** —
  build tooling; `vite.config.ts` uses `@tailwindcss/vite` since your
  `index.css` uses the Tailwind v4 `@import "tailwindcss"` / `@theme` syntax.
- **`frontend/.env`** — `VITE_API_URL=http://localhost:8000` for local dev.
- Fixed `types.ts`'s `Warehouse` interface — it declared `capacity` /
  `current_utilization` fields that `GET /warehouses` never actually returns
  (it returns the raw DB row: `warehouse_id, name, region, capacity_units`).
  Only `AuditReportsPage.tsx` consumes this type and only reads
  `name`/`region`, so nothing was broken by this, but the type was lying.

Run it:
```bash
cd frontend
npm install
npm run dev        # http://localhost:5173, talks to VITE_API_URL
# or, for production:
npm run build       # emits frontend/dist, which main.py will then serve directly
```
